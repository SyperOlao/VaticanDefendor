# Superset и аналитические дашборды

Superset 6.0.0, драйвер clickhouse-connect 1.8.0, отдельный PostgreSQL 16 для метаданных, Redis для кэша. Код инициализации и определения дашбордов находятся здесь; Весь стек определён в `../compose.yaml`. ClickHouse и его постоянный том общие с analytics; прежние базы и тома не удаляются.

## Запуск

Из корня проекта:

```sh
python3 backend/infra/superset/configure_local.py
cd backend/infra
docker compose --env-file .env -f compose.yaml up -d --build superset
docker compose --env-file .env -f compose.yaml ps -a
```

Первый запуск включает миграции Superset и занимает несколько минут. `analytics_schema` и `superset_init` завершаются с кодом 0; сервер стартует после них. Для запуска из общего Compose:

```sh
docker compose --env-file .env up -d --build superset
```

Standalone BI не требует запуска auth/game/wallet/inventory/shop/rating. Инициализация ClickHouse теперь получает только настройки warehouse; PostgreSQL inbox и service secret для неё не нужны.

Адрес: **http://127.0.0.1:28088**. Порт задаёт `VD_SUPERSET_HOST_PORT`. Вход по `VD_SUPERSET_ADMIN_USERNAME` (по умолчанию `admin`), пароль - `VD_SUPERSET_ADMIN_PASSWORD` в локальном `.env`. Скрипт настройки не печатает пароли и сохраняет существующие значения. `VD_SUPERSET_SECRET_KEY` сохраняйте вместе с метаданными: он используется для шифрования подключения в Superset.

## Дашборды

| Адрес после `/superset/dashboard/` | Вопрос страницы | Графиков |
| --- | --- | ---: |
| `vatican-runs/` | Сколько подтверждённых забегов, участников и побед? | 6 |
| `vatican-balance/` | Как отличаются версии правил и средние результаты на забег? | 6 |
| `vatican-progression/` | Сколько XP/уровней выдано и насколько полны сведения об XP? | 7 |
| `vatican-gifts/` | Какие подарки действительно получены и кем? | 5 |
| `vatican-cases/` | Какие кейсы/редкости получены и когда срабатывал гарант? | 7 |
| `vatican-shop/` | Как расходуется PRESTIGE, какие покупки платные/бесплатные? | 7 |
| `vatican-events/` | Как доставляются события и есть ли задержки/ошибки часов? | 6 |
| `vatican-bi-health/` | Успешно ли обновились все семь витрин и насколько свежи данные? | 1 |

Всего 8 дашбордов, 45 активных графиков и 8 datasets. Прежние пять URL и UUID сохранены. Баланс и подарки вынесены на самостоятельные страницы; техническая доставка отделена от состояния BI. В заголовке — ссылки на все темы. Детальные таблицы занимают всю ширину, чтобы сравнение нескольких показателей не сжималось в половину страницы. Старые графики вне этих страниц могут оставаться в списке Charts, чтобы не нарушать пользовательские ссылки и ручные дашборды.

Период по умолчанию — 30 календарных дней, включая сегодня, UTC. Используется относительный интервал от начала дня 29 дней назад до начала завтра: обычный Superset `Last 30 days` исключает сегодняшний день. Категорийные фильтры есть у забегов, баланса, кейсов, магазина и доставки. Страница состояния BI работает без фильтра периода. Таблицы/разрезы ограничены 1000 группами; для детализации сужайте фильтр. KPI считаются по всему периоду до этого ограничения и не являются суммой видимых групп.

Данные не подменяются примерами. Если фактов нет или они за пределами периода, графики пустые, счётчики равны нулю, доли/средние — без значения. Новые события проходят проекцию analytics_worker, затем обновление BI каждые 5 минут (плюс время перестройки и кэш до 60 секунд). На служебной странице кэш 15 секунд. Кнопка обновления графика не запускает перестройку витрин. Для немедленного чтения последних фактов остаются исходные представления в SQL Lab.

## Источники и смысл показателей

Bootstrap создаёт отдельную базу `vatican_bi`: семь исходных views и семь физических `*_snapshot` таблиц, семь refreshable materialized views и служебный `refresh_status`. Источники читаются с FINAL **до** копирования. По расписанию содержимое каждого снимка атомарно заменяется: повторы, исправления и поздние события не накапливаются повторно. Графики используют снимки, отсортированные по времени, без FINAL. Точность временных фильтров до миллисекунд сохраняется; суточные графики группируют факты только после фильтра. Точная уникальность игроков и средние считаются по исходным строкам периода, без суммирования суточных уникальных игроков или усреднения средних.

- Суммируется `xp_granted` забегов, а не накопленный `total_xp`. Отсутствующий XP учитывается в полноте; известный нулевой XP не считается пропуском. Разбивка не подменяет неизвестные источники нулями; частичные суммы названы известным XP. XP начислений и XP забегов не складываются между собой.
- Баланс показывает среднее на один забег, включая нулевые результаты, и число наблюдений по версии правил. Это позволяет отличать изменение поведения от роста числа игроков.
- Переход 1 → 3 — один переход и два полученных уровня. Подарки учитываются только при CLAIMED и известном claimed_at; несвязанные подарки/повышения не выдаются за конверсию.
- Кейсы — подтверждённые settlements. Наблюдаемая доля гаранта не является вероятностью выпадения из конфигурации; средний счётчик — pity_before.
- PRESTIGE — игровая валюта, **не денежная выручка**. Платные покупатели и средняя платная покупка учитывают только PRESTIGE > 0. Бесплатные выдачи выделены отдельно; разные валюты не смешиваются в расходе и средней цене, в таблице валюта показана явно.
- Участники забегов/покупатели — множества за весь выбранный период, не DAU приложения. Retention, длительность сессий, смерти, урон и карты ожидают соответствующую telemetry.
- Период доставки — **received_at**, остальные игровые страницы — время подтверждённого действия. Задержка — received_at − occurred_at последней логической записи после повторов, не время HTTP-ответа. Средняя исключает отрицательные значения; рассогласование часов показано отдельным счётчиком.
- Снимки независимы, межсервисной транзакции нет. Страница BI показывает последнее успешное обновление каждого снимка, ошибки и возраст. Более 10 минут — устаревшие данные. При сбое сохраняется предыдущий успешный снимок. Системная статистика успеха сбрасывается при перезапуске ClickHouse: до следующего успеха страница показывает отсутствие успешного обновления, а не выдуманную свежесть.

Метрики: `catalog.py`. Формы, query contexts, фильтры и сетка: `presentation.py`. SQL витрин/обновления: `serving.py` и `sql/`. Superset использует отдельного пользователя `vatican_superset`: readonly, SELECT только на BI-базу, без доступа к raw-таблицам. Web-сервис не получает пароль администратора ClickHouse. Лимиты запроса: 2 потока, 512 MiB, 30 секунд; фоновая перестройка ограничена 2 потоками, 512 MiB, 120 секундами. Расписания разнесены на 30 секунд для уменьшения одновременного старта.

Подробные ограничения, SQL-диагностика и воспроизводимый benchmark — в [PERFORMANCE.ru.md](../../docs/infra/superset/PERFORMANCE.ru.md).

## Обновление и сохранность

```sh
# Пересобрать и применить изменённые определения.
docker compose --env-file .env -f compose.yaml up -d --build superset

# Повторно применить definitions без миграций Superset.
docker compose --env-file .env -f compose.yaml run --rm --no-deps superset_init \
  /app/.venv/bin/python /app/vatican/bootstrap.py

# Логи.
docker compose --env-file .env -f compose.yaml logs -f superset superset_init

# Остановить только интерфейс, сохранив данные.
docker compose --env-file .env -f compose.yaml stop superset
```

Инициализатор использует блокировку общего `superset_home`, чтобы обычные повторные старты не запускали миграции одновременно. Созданные проектом объекты имеют стабильные UUID: повторный bootstrap обновляет их без дубликатов. Ручные правки именно этих графиков могут быть заменены definitions при следующем bootstrap; собственные варианты сохраняйте под новыми именами/UUID. Существующему администратору пароль автоматически не сбрасывается.

Постоянные тома: `superset_metadata_data`, `superset_home`, `analytics_clickhouse_data`. PostgreSQL/Redis BI не публикуют порты на хост; Superset слушает только localhost. Старый независимый Superset из другого Docker-проекта не используется и не изменяется.

## Проверка

После запуска:

```sh
docker compose --env-file .env -f compose.yaml run --rm --no-deps superset_init \
  /app/.venv/bin/python /app/vatican/verify.py
```

Проверка выполняет сохранённый query context всех 45 графиков через HTTP API, проверяет чтение `*_snapshot` без FINAL и read-only роль. В отдельных временных базах проверяются все метрики семи источников и их равенство снимкам: повторы, неизвестный XP, уровни, подарки, бесплатные покупки, разделение валют, отрицательная задержка, точные временные границы, повторное обновление, позднее исправление с переносом даты. Искусственный отказ источника проверяет сохранение последнего снимка и сигнал ошибки. Временные базы удаляются в finally; рабочие факты не меняются.

Текущие результаты измерений сохранены в [PERFORMANCE.ru.md](../../docs/infra/superset/PERFORMANCE.ru.md) и `../../docs/infra/superset/verification/benchmark.json`. На момент настройки рабочие бизнес-источники пусты: производительность измерялась на явно синтетических изолированных данных, которые удалены после проверки.
