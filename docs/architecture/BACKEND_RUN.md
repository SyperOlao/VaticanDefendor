# Этап 4: backend и локальный запуск

## Границы и данные

`backend/` — один сервис FastAPI с PostgreSQL. Unity ECS dedicated server по-прежнему выполняет симуляцию. В БД хранятся гостевые аккаунты, хеши их удостоверений, постоянные профили с версией, известные игровые процессы, забеги и поколения назначений. `permanent_currency` принадлежит постоянному профилю; клиентский API не содержит операции произвольной установки валюты. Ресурсы текущего забега остаются в ECS-сессии. Миграции: `backend/migrations/001_initial.sql` и `002_unavailable_server.sql`, запуск: `python -m vatican_backend.migrate`.

Гость создаётся `POST /v1/guests`. Backend выдаёт случайное удостоверение; в БД хранится только SHA-256 от него. Клиент передаёт его как Bearer при чтении/изменении **своего** профиля и запросе забега. Изменение профиля сейчас ограничено именем и требует ожидаемую версию. Провайдера восстановления гостя нет: потеря удостоверения означает потерю доступа к этому профилю. Для повторного запуска Unity-клиента сохраните удостоверение в защищённом хранилище запуска и передайте через `VD_GUEST_TOKEN`; локальный скрипт также читает игнорируемый `backend/.runtime/local-guest.json` с полем `token`. Без него каждый запуск создаёт нового гостя. Удостоверения не передаются в аргументах процесса, не записываются в Unity-ассеты и не печатаются сервисом.

Backend знает только заранее настроенные `serverId`, адрес/порт и отдельный секрет каждого игрового процесса. Процесс сначала слушает UDP, затем сообщает `/internal/servers/{id}/ready`. Клиентский `/v1/runs` резервирует свободный процесс и создаёт `RunId`, сервер получает назначение, копию разрешённых стартовых данных профиля и `ContentReleaseId`, подтверждает назначение через `ack`. Только после этого backend отдаёт клиенту адрес и короткоживущее HMAC-право на конкретные `AccountId`, `RunId`, `serverId` и поколение назначения. Сервер проверяет подпись, срок и активное поколение; heartbeat сверяет актуальность назначения с БД и закрывает новые подключения при потере подтверждения. При потере игрового процесса старое назначение становится `failed`; запрос того же аккаунта может получить другой свободный процесс и новый `RunId`. Присланный клиентом `AccountId` или хеш контента не является авторизацией. Один процесс держит один забег и одного игрока. Несколько процессов задаются отдельными элементами `VD_SERVER_POOL_JSON`; каждому нужны свой ID, секрет и UDP-порт.

`/v1/*` принимает гостевое Bearer-удостоверение; `/internal/*` требует секрет соответствующего игрового процесса. Клиентское удостоверение не открывает внутренние маршруты. Backend HTTP для Unity требует HTTPS с обычной проверкой сертификата. Явный `-vdInsecureLocalBackend` разрешает HTTP только на loopback. Текущий игровой UDP транспорт не шифруется: backend-режим ограничен loopback-адресами в конфигурации сервиса, в клиентском назначении и в bind сервера. Для удалённого deployment необходим DTLS/защищённый транспорт и TLS-терминация HTTP; эта конфигурация не заявляется как готовая к production. `-vdDevelopmentIdentity` остаётся отдельным режимом только Development Build и не включается автоматически.

## Воспроизводимый запуск

Нужны Docker Desktop с работающим daemon, Unity 6000.6.6f1 и собранные Development Player. Из корня проекта:

```powershell
pwsh -File backend/scripts/start-local.ps1
& 'C:\Program Files\Unity\Hub\Editor\6000.6.6f1\Editor\Unity.exe' -batchmode -nographics -quit -projectPath . -executeMethod VaticanDefendor.Editor.NetworkPrototypeBuild.BuildServer -logFile Builds/Stage4-server-build.log
& 'C:\Program Files\Unity\Hub\Editor\6000.6.6f1\Editor\Unity.exe' -batchmode -nographics -quit -projectPath . -executeMethod VaticanDefendor.Editor.NetworkPrototypeBuild.BuildClient -logFile Builds/Stage4-client-build.log
```

Запустите в **разных** терминалах:

```powershell
pwsh -File backend/scripts/run-server.ps1
pwsh -File backend/scripts/run-client.ps1
```

`run-client.ps1 -Headless -Move 0.5,0` даёт проверяемый ввод без окна. Скрипт `start-local.ps1` создаёт случайные локальные секреты в игнорируемом `backend/.runtime/`, поднимает БД и API и ждёт `/health/ready`. Для ручного запуска конфигурация задаётся `VD_DATABASE_URL`, `VD_SERVER_POOL_JSON` и необязательным `VD_GRANT_TTL_SECONDS` (10–600). Пример **формата без действующих секретов**: `backend/.env.example`; для второго процесса создайте отдельный slot и запустите dedicated player с его `-vdServerId`, `-vdPort` и `VD_SERVER_SECRET`. Проверка готовности делает реальный запрос к БД и проверяет применённую миграцию. `GET /health/live` проверяет только процесс.

## Проверки и ограничения

`backend/tests/test_api.py` требует отдельную PostgreSQL БД через `VD_TEST_DATABASE_URL` и проверяет долговечность профиля при создании нового приложения, разграничение A/B, запрет `SetCurrency`, секрет сервера, резервирование и подтверждение процесса, чужое/устаревшее/просроченное право. `backend/tests/write_unity_grant_cases.py` и `VaticanDefendor.Editor.BackendGrantVerification.Verify` сверяют реальные Python-подписи с C#-проверкой, включая отказ для чужого аккаунта/сервера, истёкшего и отозванного назначения. Оба теста используют только игнорируемые локальные fixtures. Многопроцессная проверка должна видеть `[Server] Backend assigned`, `Approved`, `Spawned hero` и изменение `position=` в `Builds/Stage4/server.log`.

Ограничения гостевого режима: отсутствуют восстановление удостоверения и привязка к платформенному аккаунту. Отсутствует гарантия возобновления ECS-забега после падения процесса (этап 10). Изменение постоянной валюты будет добавляться только как доверенная серверная операция вместе с фактическими правилами наград (этап 8). Смена назначения при живом старом игровом процессе запрещает новые входы после heartbeat, но уже одобренное соединение не разрывается принудительно; это следует завершить при реализации reconnect/восстановления.
