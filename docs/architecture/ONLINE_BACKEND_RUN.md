# Online backend: запуск и границы

Реализация продолжает существующие FastAPI/PostgreSQL и Unity Netcode for Entities 6.6.0. План и результаты проверок: [ONLINE_BACKEND_PLAN.md](ONLINE_BACKEND_PLAN.md). Android/iOS используют логин/пароль; Google/Apple отложены по уточнению пользователя. Платежи за реальные деньги не реализуются.

## База и API

Установить `backend/requirements.txt` в отдельное окружение Python 3.12. Задать `VD_DATABASE_URL`, `VD_SERVER_POOL_JSON`, `VD_RUN_REWARDS_JSON`. Применить `python -m vatican_backend.migrate` из `backend`; миграция `006_online_backend` добавляет таблицы аккаунтов, сессий, публикаций, инвентаря и покупок без удаления существующих данных. Миграции сериализованы advisory lock. Запуск: `uvicorn vatican_backend.api:create_app --factory --host 127.0.0.1 --port 8080`.

`VD_DB_POOL_SIZE` (по умолчанию 10) ограничивает подключения на один API-процесс. Учитывать сумму пулов при увеличении числа workers. Пул живёт в FastAPI lifespan. Переполнение/таймаут пула возвращают 503.

`POST /v1/runs` с `Prefer: respond-async` быстро возвращает 202 и `Location: /v1/runs/{id}`. Клиент опрашивает этот адрес до готового назначения, с отменой и общим сроком ожидания. Старый синхронный маршрут сохранён для существующих стендов. Повтор запроса аккаунта возвращает тот же живой забег. Серверная архитектура пока сохраняет один процесс на забег; автоматический fleet allocator не добавлен.

## HTTPS и DTLS

Для API можно использовать `docker compose -f compose.yaml -f compose.online.yaml up -d --build` из `backend`, с заполненными внешними переменными и `VD_API_HOST`. DNS должен указывать на сервер; 80/443 доступны Caddy для получения сертификата. PostgreSQL и прямой HTTP API по-прежнему привязаны к loopback хоста. Не помещать реальные `.env`, пароли, приватные ключи или runtime JSON в Git.

В серверном slot добавить `"transport":"dtls"` и `"certificateName":"game.example.org"`, а `host` задать публичным IPv4. Публичный адрес назначения отличается от локального bind. Dedicated-процесс запускать с `-vdDtls -vdBind 0.0.0.0`, прежними `-vdServerId`, `-vdPort`, HTTPS `-vdBackendUrl`, переменными `VD_SERVER_SECRET`, `VD_DTLS_CERT_FILE`, `VD_DTLS_KEY_FILE`. Открыть выбранный UDP-порт. Сертификат должен соответствовать `certificateName`; ключ остаётся только на сервере.

Клиентский DTLS проверяет серверный сертификат по доверенному CA и имени. На desktop CA читается из `VD_DTLS_CA_FILE`; на телефоне — из `Resources/NetworkDeployment.asset`. Нет режима обхода проверки сертификата. Удалённые plaintext UDP назначения запрещены. `udp-loopback` остаётся для локального стенда. Настроенный transport проверяется при регистрации и recovery сервера. Симулятор потерь не может заменить защищённый драйвер.

## Android/iOS и экран аккаунта

Через Create > VaticanDefendor > Network > Deployment Settings создать `Assets/Resources/NetworkDeployment.asset`. В Inspector задать HTTPS backend URL и **публичный** PEM CA игрового сервера. В мобильной сборке роль по умолчанию — client. Endpoint не должен быть localhost: на телефоне это сам телефон. Пароли и секреты серверов в asset не помещаются.

Клиент показывает экран входа, регистрации и восстановления. Длина логина 3–64 (`A-Z`, `a-z`, цифры, `_ . -`), пароль 6–128 символов. Логин регистронезависим. Регистрация с уже переданным `VD_GUEST_TOKEN` привязывает его профиль и отзывает гостевое удостоверение; при регистрации нового аккаунта создаётся новый профиль. При входе в иной аккаунт профили автоматически не объединяются.

Пароли хешируются Argon2id; opaque access/refresh-токены хранятся в БД как SHA-256. Access действует 15 минут, refresh — 30 дней и заменяется при использовании. Конкурентный повтор refresh получает 401. Клиент обновляет сессию перед API-запросами, включая reconnect. При потере ответа на refresh может понадобиться повторный вход. Лимиты попыток общие для API workers (БД), по адресу подключения и логину. При reverse proxy нужно корректно настроить доверенные proxy addresses Uvicorn; не доверять произвольным X-Forwarded-For.

Одноразовый код восстановления выдаётся при регистрации и после смены пароля по старому коду; UI предлагает сохранить его. Восстановление отзывает прежние backend-сессии и гостевые удостоверения. Активный уже одобренный игровой UDP-сеанс не является backend bearer-сессией: его принудительное завершение при смене пароля в этой версии не реализовано.

Токены и пароль не сохраняются в PlayerPrefs или файлы телефона: после перезапуска нужен вход. Для автоматического входа в будущем потребуется отдельное защищённое хранилище Keychain/Android Keystore. Headless проверки могут передавать `VD_LOGIN` и `VD_PASSWORD` через окружение; существующий гостевой headless-стенд сохранён. Не передавать пароль в аргументах процесса.

## Версии конфигов

Дизайнер продолжает редактировать существующие типизированные определения и собирать ContentRelease. Выбрать готовый release и выполнить `VaticanDefendor > Content > Export Selected Release JSON`. Экспорт проверяет канонический ID и добавляет SHA-256 JSON-полезной нагрузки. Формула существующего ID сохранена, перенесена в runtime `ContentReleaseHash`.

Публикация: задать `VD_BACKEND_URL`, `VD_CONTENT_ADMIN_SECRET`, выполнить `python scripts/publish-content.py <export.json>` из `backend`. Для localhost-стенда явно добавить `--allow-local-http`. Секрет публикации независим от игровых серверных секретов. Повтор идентичной публикации разрешён; изменение содержимого под существующим ID получает 409.

Сервер может получить опубликованный release при старте через `VD_CONTENT_RELEASE_ID`. Клиент скачивает точный release из назначения, если он отличается от встроенного. Перед созданием World проверяются версия схемы, SHA-256 JSON и канонический хеш всех определений. Подмена файла не создаёт игровую сессию. Полученные ScriptableObject принадлежат startup и уничтожаются при завершении. Работающий забег и checkpoint сохраняют прежний release; обновление конфига применяется к новым процессам/забегам. Для нового release также нужна утверждённая политика `VD_RUN_REWARDS_JSON`.

API проверяет контрольную сумму и оболочку публикации; полная проверка структуры и канонического игрового хеша выполняется Unity exporter/loader. Публиковать следует только экспорт валидированного ContentRelease. Формат не предназначен для загрузки новых моделей, сцен или исполнения кода.

## Каталог, покупки и инвентарь

`backend/shop-catalog.json` изначально пуст. В Docker он подключён read-only, в обычном запуске задаётся `VD_SHOP_CATALOG_FILE`; альтернативно допустим `VD_SHOP_CATALOG_JSON` (одновременно оба запрещены). После изменения конфигурации перезапустить API. При каждом изменении предложений менять `version`.

Конфиг: `version` (до 64 латинских букв/цифр/`_.-`), массив `offers` (до 200). Каждое предложение содержит ровно:

- `id`: стабильный ID предложения, `[a-z0-9_.-]`, до 64 символов;
- `itemId`: ID выдаваемого предмета, такой же формат;
- `title`: отображаемое название, 1–80 символов;
- `price`: стоимость в постоянной валюте, положительное целое;
- `quantity`: выдаваемое количество, положительное целое;
- `maxOwned`: предел количества предмета у игрока, не меньше quantity.

Значения price/quantity/maxOwned ограничены 1 000 000 000. Товары и цены не придуманы и не включены в рабочий конфиг. Купленные записи попадают в инвентарь; конкретные эффекты предметов/экипировка требуют продуктового определения и не подменяются произвольной формулой.

`GET /v1/shop`, `GET /v1/inventory`, `POST /v1/purchases` доступны только владельцу аккаунта. Покупка содержит operationId (UUID), offerId, catalogVersion; цену и результат клиент не задаёт. Под блокировкой строки профиля backend проверяет средства и лимит, списывает валюту, выдаёт предмет и сохраняет receipt в одной транзакции. Повтор возвращает прежний receipt даже после удаления предложения. Конфликт operationId — 409. `GET /v1/purchases/{operationId}` позволяет выяснить результат потерянного ответа.

Клиент сохраняет только незавершённое намерение покупки (без credentials) в `Application.persistentDataPath`, отдельно по account ID. После таймаута/перезапуска проверяет receipt и повторяет прежний operationId; новая операция не создаётся до разрешения предыдущей. Журнал удаляется после подтверждения либо окончательного отказа. Награды за забег продолжают использовать существующую серверную транзакцию и дисковый журнал доставки.

## Проверки

`VD_TEST_DATABASE_URL` должен указывать **только на disposable PostgreSQL**: fixture очищает данные. Команда: `python -m pytest -q` из backend. Новые проверки включают привязку/восстановление аккаунта, отзыв и конкурентный refresh, лимиты входа, конкурентные покупки, повтор и конфликт operationId, изоляцию инвентаря, публикацию и неизменяемость конфигов, async assignment, запрет удалённого plaintext транспорта.

Unity: `-executeMethod VaticanDefendor.Editor.OnlineBackendVerification.Verify` проверяет реальный текущий ContentRelease, JSON roundtrip, отказ изменённому балансу и требование DTLS для удалённого назначения. Методы `NetworkPrototypeBuild.BuildMacClient` / `BuildMacServer` позволяют проверить установленный macOS toolchain, существующие Windows методы сохранены. Android/iOS требуют соответствующих модулей Unity, signing и проверки на устройствах.

## Быстрый локальный запуск на macOS

Добавлен launcher `backend/scripts/local.py` (стандартная библиотека Python 3). Он сам определяет выбранный ContentRelease и использует совместимый с PowerShell-стендом `.runtime/local.json`; секреты не печатаются. Для сборки закрыть проект в Unity. Нужны запущенный Docker Desktop и модуль Mac Dedicated Server Build Support для версии Editor из ProjectVersion.txt.

Из корня проекта:

```sh
python3 backend/scripts/local.py build-server
python3 backend/scripts/local.py backend --reward-per-church-level 1
```

`1` здесь — явно тестовая награда для локального запуска, не утверждённый баланс. Каталог товаров остаётся пустым. Backend запускается в Docker в фоне. В отдельных терминалах из корня проекта:

```sh
python3 backend/scripts/local.py server
```

```sh
python3 backend/scripts/local.py client
```

Клиент уже собран в Builds/OnlineMac/Client. При изменении C# или контента пересобрать: `python3 backend/scripts/local.py build-client` (сервер тоже пересобрать при изменении общих правил). На экране клиента зарегистрироваться или войти, сохранить код восстановления при регистрации, затем нажать «Начать / продолжить забег», а на игровом экране — «Start» для подключения. Без запущенного игрового сервера начать забег нельзя.

`local.py status` показывает выбранный release и наличие сборок. `local.py logs` выводит логи API. Для остановки client/server завершить соответствующие процессы (Ctrl+C в терминалах); `local.py stop` останавливает Docker-сервисы, сохраняя PostgreSQL volume и профили. Не удалять volume для обычного перезапуска.

Этот launcher работает на одном Mac через loopback. Для телефона нужны отдельные HTTPS/DTLS настройки из разделов выше.

## Локальный клиент и сервер в Unity Editor

Обычный Play из `ActiveCombat` или `NetworkPrototype` запускает клиентский и серверный ECS Worlds внутри Editor. Отдельная серверная сборка и backend не требуются. Используются текущие исходники и общий выбранный ContentRelease, временная тестовая identity и свободный порт выбранного транспорта. Аккаунт и постоянные награды не записываются. Stop завершает оба Worlds; следующий Play создаёт новый матч. Доступна также команда **VaticanDefendor > Network > Play Client and Server in Editor**. В локальном режиме кнопка «Новый матч» пересоздаёт пару Worlds.

## Онлайн-клиент в Unity Editor и Device Simulator

Запустить backend (`python3 backend/scripts/local.py backend --reward-per-church-level 1`) и игровой сервер (`python3 backend/scripts/local.py server`) в отдельных терминалах из корня проекта. Для первого запуска сервер предварительно собрать через `build-server` при закрытом Editor.

В редакторе выполнить **VaticanDefendor > Network > Play Local Online**. Команда на время Play Mode выбирает `NetworkPrototype` как стартовую сцену и loopback backend `http://127.0.0.1:8080`. После Stop восстанавливаются предыдущая сцена редактора и настройка стартовой сцены; release/mobile deployment не меняется. Эта команда использует внешний игровой сервер и проверяет настоящий профиль; обычный Play запускает локальную пару Worlds. Явно заданные CLI-параметры сохраняют своё поведение.

Открыть **Window > General > Device Simulator**, либо переключить `Game` на `Simulator` в левом верхнем выпадающем списке Game view. Выбрать модель телефона и портретную ориентацию. Это проверка размеров экрана и касаний в Editor, а не полноценная эмуляция Android/iOS. Для ввода использовать клавиатуру Mac. Зарегистрироваться или войти, затем нажать «Начать / продолжить забег» и «Обычная игра» (Start).

При одном открытом Game/Simulator view на экране входа доступна проверка **VaticanDefendor > Network > Verify Online Account Input**: она подаёт события временного устройства Mouse через Input System, проверяет попадание в поля, фокус и обработку текстового события; аккаунт не создаётся и запросов к API нет. После проверки устройство удаляется, исходный текст восстанавливается.

На Mac клиент и сервер также собираются из открытого редактора: **VaticanDefendor > Network > Build Mac Client / Build Mac Server** (выйти из Play Mode). Для проверки телефона предпочтительно переключать существующую вкладку Game в Simulator, чтобы не держать два игровых окна одновременно.

Проверка исправлений подключения: **VaticanDefendor > Client > Verify Connection Transitions** проверяет запись ECS-состояния при подключении, сброс синхронизации и отключение. После авторизации клиент явно загружает auto-load SubScene в созданный World и ждёт завершения загрузки перед отправкой JoinApproval.

**Выйти из аккаунта** доступно в профиле и отдельной кнопкой в правом верхнем углу игрового экрана. Выход отключает транспорт, выгружает игровую сцену/World, отзывает текущую backend-сессию и очищает токены в памяти. Профиль, валюта и журнал незавершённых покупок сохраняются. При недоступном API выполняется локальный выход с явным сообщением; удалённая сессия в таком случае может оставаться действительной до истечения срока.

**VaticanDefendor > Network > Verify Online Play And Logout** запускается на экране входа с работающим локальным backend/server. Создаёт отдельный аккаунт `verify_*`, проверяет регистрацию, выход из профиля, два цикла вход → бой с героем → выход, удаление World и отказ отозванному токену. Забег проверочного аккаунта занимает локальный сервер до завершения/истечения удержания; запускать на свободном тестовом сервере.
