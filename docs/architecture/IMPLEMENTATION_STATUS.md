## Подтверждение этапа 1

- Источник новых базовых скоростей — сохранённый `Assets/ActiveCombat/Settings/CombatBalance.asset`: `WalkSpeed` 4.8 м/с и `RunSpeed` 8.6 м/с. Значения в удалённом коде по умолчанию совпадали; удалённая симуляция дополнительно применяла множитель прогрессии и логику жестов. Эти механики не объединялись с новым базовым определением и будут подключаться только в соответствующих этапах.
- `HeroMovement.asset` — типизированный дизайнерский authoring со стабильным ID и закрытыми сериализуемыми полями. `MovementCatalog.asset` задаёт включённые определения и ссылку на используемое по умолчанию. Генератор отклоняет пустые ссылки, дубли ID, неправильный ID, нечисловую/неположительную скорость, скорость выше 100 м/с и бег медленнее ходьбы. Диагностика содержит путь ассета и имя поля.
- Меню Unity `VaticanDefendor > Content > Build Selected Release` строит release из выбранного `MovementCatalog.asset`. Манифест сортируется по стабильному ID; SHA-256 считается по явно записанным UTF-8 строкам и числам в invariant round-trip формате, включая версию формата, вид определения и связи. Повторная сборка тех же значений возвращает существующий `Assets/ActiveCombat/Content/Releases/sha256-f2866c0305868d0920ef46a4fec4b07093c5115785080b395bccaa09cda748a0.asset`, не переписывая его. Смена значения создаёт новый asset и ID; существующий release проверяется перед повторным использованием.
- `HeroMovementSession.Create` — одноразовая граница запуска серверной сессии этапа 1. Она копирует скорость и ID release в ECS-компоненты героя. На этапе 2 тот же снимок используется при создании сетевого ghost через `HeroMovementSession.Instantiate`; `HeroMovementSystem` читает `HeroMoveInput`, `HeroMovementTuning` и `LocalTransform` в server/client predicted simulation, без ScriptableObject/JSON в tick. Старый герой сохраняет свой снимок после появления нового release. Для одного героя BlobAsset не даёт выгоды; массовые определения будущих модулей потребуют отдельного решения о BlobAsset и сроке жизни памяти.
- Через меню `VaticanDefendor > Content > Verify Movement Release` в Unity 6000.6.6f1 выполнена проверка на реальном `WorldFlags.GameServer`: за 1 секунду герой проходит 4.8 м с исходным release, новый release с авторской скоростью +1 м/с меняет дистанцию, режим бега использует свою скорость, старый герой сохраняет исходные параметры и ID. Проверены повторяемость сборки, отказы на неверных диапазонах, пустой/посторонней ссылке и дублирующемся ID. После импорта Console показывает 0 ошибок; остаётся прежнее предупреждение Entities Graphics.
- `ContentRelease.ReleaseId` описывает только содержимое и формат его манифеста. Версия сетевого протокола и версия сохраняемого состояния будут отдельными контрактами на этапах 2 и 10. ID или хеш, присланный клиентом, не служит доказательством личности, доступа или права выбрать release: сервер выбирает release из доверенных локальных данных. Секреты и серверные удостоверения в ассеты не добавлялись.

## Подтверждение этапа 2

- Фактический стек: Unity 6000.6.6f1, Entities/Entities Graphics/Netcode for Entities/Unity Transport 6.6.0. Дополнительный сетевой фреймворк не добавлялся. Установлен модуль Windows Dedicated Server для этого Editor; обе Development Build завершились `Build Finished, Result: Success` в `Builds/Stage2/client-rebuild2.log` и `Builds/Stage2/server-rebuild2.log`.
- `NetworkPrototypeBootstrap` создаёт ровно один Client или Server World по роли и освобождает его при завершении. Серверный процесс запускает `ServerCompositionRoot`, закрепляет один `RunSession` с GUID `RunId`, доверенным `AccountId` из server environment и `ContentReleaseId` из локально выбранного release. В dedicated-сцене нет UI и камеры; симуляция зависит от ECS-компонентов, не от rendering. Проверено содержимое server player DLL: клиентские `ClientMoveInputSystem` и `ClientPrototypeView` отсутствуют благодаря `UNITY_SERVER`.
- `JoinApproval` передаётся как `IApprovalRpcCommand` через Unity Transport в состоянии `Approval`. Сервер отдельно проверяет версию игрового протокола, release, RunId и заранее назначенный development ticket, затем одобряет соединение и создаёт принадлежащий NetworkId ghost. Клиентский `AccountId` не принимается. Development-адаптер требует Development Build и явный `-vdDevelopmentIdentity`; запуск без этого флага проверен отдельно: сообщение `Production identity provider is not configured`, код выхода 2.
- `HeroMoveInput` содержит направление и флаг бега. Сервер отбрасывает NaN/Infinity и неверный флаг, нормализует вектор длиной больше 1 и использует скорость из закреплённого release. Ghost задан как owner-predicted; Netcode доставляет input и snapshots, а `HeroMovementSystem` выполняет повторяемое движение без внешних эффектов. Клиентское отображение следует `GhostOwnerIsLocal` и показывает статус соединения. Из-за аварии внутреннего Burst job `Unity.NetCode.GhostOwnerUpdateSystem` в установленном Netcode 6.6.0 на Windows Development Player клиентский composition root исключает только эту систему и использует `ClientGhostOwnerSystem` с тем же порядком после `GhostUpdateSystem`; повторный многопроцессный запуск после замены не падает.
- Реальный прогон: сервер A на UDP 7979 с `RunId=11111111-...`, сервер B на UDP 7980 с `RunId=22222222-...`; два независимых клиентских процесса. A с `-vdMove 1000,0` менял авторитетную позицию примерно на 4,8 м каждую секунду (`2,80 → 7,60 → 12,40`), B с `-vdMove 0,0` оставался на `(0,0)`. Оба клиента получили approval и реплицированный ghost; в логах есть `predictedPosition`. Чужой ticket получил `Unauthorized`, верный ticket с `sha256-invalid` получил `ContentMismatch`, второй одновременный клиент получил `RunOccupied`; причины дошли до клиентов до disconnect. После остановки клиента сервер зарегистрировал `Released disconnected player`, затем новый разрешённый клиент вновь получил героя.
- Графический клиент открывал окно, показывал текстовый статус и продолжал обновлять реплицированный ghost. Запрос Windows Security на доступ executable к публичным сетям перекрыл большую часть окна; настройки Firewall не менялись, поэтому визуальное движение капсулы отдельно не подтверждено. Headless клиент и server выполняли полный сетевой цикл. После принудительной потери клиента сервер продолжает применять последний input до сетевого timeout; затем уничтожает героя и освобождает слот. Повторное подключение пока начинает героя заново, восстановление забега относится к этапам 9–10. Development ticket не предназначен для production.
- При создании сетевой сцены исходная несохранённая Editor-сцена была сохранена как `Assets/ActiveCombat/Network/EditorWorkspaceBackup.unity`, чтобы не потерять открытое пользовательское состояние; в player build включена только `NetworkPrototype.unity`.

Для каждого следующего этапа действуют те же требования: рабочее поведение, потребители, проверка и запись фактического результата. Пустые интерфейсы, no-op и фиктивный успех не повышают статус.

## Этап 3: клиентский Shell, MVP и ввод

- `ClientShellPresenter` координирует Launch, Connecting, Game, Menu, Settings, Lost и Error через `IClientShellView` и `IClientSessionPort`. `ClientShellViewModel` описывает данные экрана. `ClientShellView` привязан к сохранённым `MainMenu`, `PauseOverlay`, `SettingsModal`, двум `CombatRenderSurface` и `Knight.prefab`; значения `CombatBalance.MobileView` применяются только к локальному представлению. Старые индикаторы здоровья, ресурсов, волн и строительства скрыты, поскольку сервер этих данных и действий ещё не публикует.
- Ввод с клавиатуры и касаний проходит через `ClientMoveIntent` и `ClientMoveInputSystem` в существующий Netcode input. UI не записывает авторитетные ECS-компоненты. `PointerOwnership` закрепляет pointer за UI, картой, боем или разделителем и освобождает его при завершении жеста и выключении поверхности. Верхний маркер и нижний Knight следуют одному локальному ghost. Локальное меню обнуляет намерение движения, но не останавливает серверную симуляцию.
