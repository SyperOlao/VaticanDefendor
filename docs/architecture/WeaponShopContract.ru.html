Контракт магазина оружия за престиж

Дата: 12 ноября 2026 года. Версия контракта: 1.

Магазин продаёт оружие за существующий постоянный престиж аккаунта. Unity реализует клиентскую часть; backend реализуется отдельно по этому контракту. Описание задаёт целевое поведение и не означает, что API уже реализовано.

Правила покупки

  • Магазин доступен в лобби. Дерево, камень и железо текущего матча не участвуют в оплате.
  • Идентификатор валюты — prestige. Это тот же баланс, который существующий GET /v1/profile возвращает в permanentCurrency; второй кошелёк не создаётся.
  • Одна покупка выдаёт один уникальный экземпляр оружия. Цена — целое неотрицательное число единиц престижа, без дробной части.
  • Повторная покупка той же конфигурации создаёт новый InstanceId, если предложение допускает повторные покупки. Экземпляры имеют независимую прогрессию.
  • Купленное оружие появляется в инвентаре предматчевого выбора. Покупка не меняет выбранное снаряжение автоматически. Лимит выбора — три экземпляра.
  • Снаряжение уже начатого забега остаётся закреплённым за его RunId. Покупка не добавляет оружие в этот забег.
  • Новый аккаунт по-прежнему получает только стартовый меч. Награды за матч и покупки — отдельные способы пополнения одного инвентаря.

Владельцы данных

Backend владеет балансом престижа, каталогом, ценами, доступностью предложений, конфигурациями оружия, экземплярами и результатами покупок. Он определяет аккаунт из авторизации.

Unity получает данные, показывает карточки и отправляет намерение купить предложение. Клиент не передаёт цену, баланс, характеристики оружия, редкость, уровень, количество выдаваемых экземпляров или свой accountId для назначения получателя.

Все запросы используют существующий HTTPS API и заголовок Authorization: Bearer <accessToken>. Покупка относится к backend аккаунта, а не к Netcode-командам или RPC игровой симуляции.

API

Метод и путь Назначение
GET /v1/shop Получить каталог, конфигурации продаваемого оружия и баланс.
POST /v1/purchases Купить одно предложение с защитой от повторного выполнения.
GET /v1/purchases/{operationId} Уточнить результат операции текущего аккаунта.
GET /v1/weapons Получить актуальные экземпляры, конфигурации и выбранное снаряжение.

Каталог

Ответ GET /v1/shop содержит следующие поля:

Поле Тип Значение
version string Непрозрачная версия снимка предложений, цен и связанных конфигураций. Клиент не сравнивает версии лексикографически.
currencyId string Всегда prestige в первой версии.
walletBalance int64 Подтверждённый баланс того же кошелька, что permanentCurrency.
walletRevision int64 Монотонная версия кошелька аккаунта.
offers array Предложения для этого аккаунта. Пустой массив допустим.
configurations array Полные WeaponConfiguration для предложений, включая ещё не приобретённое оружие.

Пример предложения из offers:

{
  "id": "offer_spear_rare",
  "weaponConfigurationId": "spear_rare_01",
  "title": "Редкое копьё",
  "price": 150,
  "currencyId": "prestige",
  "available": true,
  "unavailableReason": "",
  "purchaseLimit": 0,
  "purchasedCount": 0
}

id идентифицирует предложение, weaponConfigurationId — конфигурацию выдаваемого оружия. Это разные идентификаторы. Покупаемый InstanceId создаётся только сервером при успешной операции.

purchaseLimit = 0 означает отсутствие ограничения. Иначе это максимальное число успешных покупок данного предложения аккаунтом; purchasedCount показывает уже использованное количество. Наличие другого экземпляра той же конфигурации само по себе не запрещает покупку.

При available = false поле unavailableReason содержит машинный код причины, например OfferUnavailable или PurchaseLimitReached. Проверка достаточности показанного баланса в Unity служит для состояния кнопки; окончательную проверку выполняет backend.

Формат элементов configurations совпадает с существующим WeaponConfiguration из Assets/Scripts/Foundation/WeaponConfiguration.cs, включая текущий PascalCase его полей. Он содержит название, иконку, изображение, редкость, модель, боевые параметры, прогрессию и идентификаторы способностей. Unity не загружает исполняемый код способностей: их виды реализованы в клиенте и игровой симуляции.

Ссылка предложения должна разрешаться в конфигурацию того же ответа. Изменение цены, выдаваемой конфигурации или её параметров меняет версию каталога. Уже приобретённый экземпляр должен однозначно разрешаться в свою серверную конфигурацию; миграция существующих экземпляров не выполняется молча как часть покупки.

Запрос покупки

Тело POST /v1/purchases:

{
  "operationId": "b207e814-926e-4db9-bb54-aaf4df6844db",
  "offerId": "offer_spear_rare",
  "catalogVersion": "shop-12"
}

Unity создаёт новый UUID для нового намерения купить и сохраняет запрос локально до отправки. Повтор после таймаута использует те же три значения. Количество всегда равно одному экземпляру и в запрос не входит.

Backend проверяет авторизацию, версию каталога, существование и доступность предложения, лимит покупок и фактический баланс. Списание, создание экземпляра, изменение ревизий и сохранение результата применяются одной атомарной операцией. При отклонении престиж и инвентарь не меняются.

Успешный результат

POST /v1/purchases возвращает HTTP 200 и результат:

{
  "operationId": "b207e814-926e-4db9-bb54-aaf4df6844db",
  "status": "Completed",
  "offerId": "offer_spear_rare",
  "chargedAmount": 150,
  "currencyId": "prestige",
  "walletBalance": 350,
  "walletRevision": 18,
  "inventoryRevision": 27,
  "grantedWeaponInstanceIds": [
    "a1a579e7-b897-4d6c-a5cc-61753424bfc3"
  ],
  "replayed": false
}

В первой версии grantedWeaponInstanceIds содержит ровно один ID. Ответ подтверждает выдачу; Unity не создаёт локальный предмет самостоятельно.

После Completed Unity обновляет инвентарь через GET /v1/weapons. Его существующая структура сохраняется: Configurations, Weapons, Loadout, Revision. Каждый элемент Weapons содержит InstanceId, ConfigurationId, Level, Experience. Начальный уровень и опыт задаёт backend.

Следующее чтение инвентаря после завершённой покупки должно вернуть Revision не ниже inventoryRevision результата и включать выданный экземпляр. Если обновление инвентаря временно не удалось, UI показывает, что покупка подтверждена, а загрузка инвентаря требует повтора. Новая покупка вместо этого не создаётся.

Проверка результата

GET /v1/purchases/{operationId} ищет операцию только в аккаунте авторизованного пользователя.

  • HTTP 200 с status = Completed возвращает сохранённый успешный результат.
  • HTTP 200 с status = Rejected возвращает окончательное отклонение и его code.
  • HTTP 404 с code = OperationNotFound означает, что сохранённый результат пока не найден. Это не доказательство, что параллельный исходный запрос не завершится. Unity может повторить исходный POST с прежним ID и содержимым.

Пример сохранённого отклонения:

{
  "operationId": "b207e814-926e-4db9-bb54-aaf4df6844db",
  "status": "Rejected",
  "offerId": "offer_spear_rare",
  "code": "InsufficientFunds",
  "replayed": true
}

Повторы и потеря ответа

Ключ идемпотентности — пара авторизованный аккаунт и operationId. Backend сохраняет исходное содержимое запроса и окончательный результат. Параллельные одинаковые запросы не могут создать два списания или два экземпляра.

Повтор завершённой операции возвращает прежний результат с replayed = true. Сначала проверяется существующая операция: последующее изменение каталога или баланса не должно превращать повтор уже успешной покупки в отказ.

Повтор того же ID с другим offerId или catalogVersion возвращает OperationConflict; исходная операция не меняется. Unity сохраняет её журнал и уточняет результат по ID. Новый ID не используется для автоматического обхода конфликта.

Результаты и защита от повторного выполнения сохраняются между перезапусками backend и в течение жизни аккаунта. Ранее использованный ID не становится новым намерением после очистки временного кеша.

Unity хранит журнал незавершённой покупки отдельно для аккаунта, без токенов и паролей. Таймаут, разрыв соединения, отмена ожидания или HTTP 5xx оставляют результат неизвестным. Закрытие окна магазина не отменяет уже отправленную серверную операцию.

После повторного входа Unity сначала разрешает незавершённую операцию. Пока её исход неизвестен, новое намерение покупки на этом клиенте не отправляется. Журнал удаляется после подтверждённого Completed или Rejected; не по одному факту HTTP 404 или 409.

Ошибки и версии состояния

Машинный код обязателен. Текст интерфейса выбирается на клиенте по коду, а не по сравнению строк сообщения сервера.

HTTP при POST code Реакция Unity
400 InvalidRequest Показать ошибку запроса; не повторять автоматически с новым ID.
401 Unauthorized Применить существующий механизм авторизации; при повторе сохранить ID операции.
409 InsufficientFunds После подтверждённого отказа обновить баланс и показать нехватку престижа.
409 CatalogChanged После подтверждённого отказа обновить каталог. Покупка по новой цене требует нового нажатия и нового ID.
409 OfferUnavailable После подтверждённого отказа обновить каталог и доступность карточки.
409 PurchaseLimitReached После подтверждённого отказа обновить счётчик и состояние предложения.
409 OperationConflict Сохранить журнал и запросить результат исходной операции.
429 или 5xx Код сервиса Сохранить журнал; повторить проверку с задержкой, учитывая Retry-After, если он задан.

Окончательный бизнес-отказ POST содержит operationId, status = Rejected и code в том же формате, что проверка результата. Ошибка авторизации или транспорта сама по себе не является результатом покупки.

Unity принимает баланс только с walletRevision не ниже уже принятой. Инвентарь принимается только с Revision не ниже текущей. При чтении старого GET /v1/profile без ревизии кошелька Unity не должна откатывать более свежий подтверждённый баланс покупки; для магазина баланс обновляется через ревизионный ответ каталога или результата.

Проверка лимита, остатка престижа и изменение ревизий должны оставаться согласованными при покупках с нескольких устройств. Ревизии кошелька и инвентаря независимы.

Область Unity реализации

Unity реализует транспортные DTO и клиент API, Model–View–Presenter магазина, карточки оружия, подтверждение цены, блокировку повторного нажатия, загрузку изображений, обработку ошибок, журнал операции и обновление инвентаря.

Экран различает загрузку, пустой каталог, готовность купить, недоступность предложения, ожидание покупки, неизвестный результат и подтверждённую покупку. При ошибке изображения сохраняются название, характеристики, цена и возможность работать с карточкой.

Backend реализуется отдельно: обработчики API, авторизация, каталог, транзакции, идемпотентность, кошелёк и выдача экземпляров. В этой задаче Unity не изменяет серверный код или базу данных. Локальный тестовый адаптер допустим для разработки UI, но не выдаёт оружие в настоящий аккаунт и не считается серверной реализацией.

Текущие общие ShopOffer, PurchaseReceipt и магазин в OnlineAccountPresenter требуют адаптации к этому контракту. Учёт обычных itemId и quantity не заменяет выдачу уникального экземпляра оружия. Существующее удаление журнала по любому HTTP 404 или 409 должно быть заменено разбором результата операции.

Проверки интеграции

  1. Обычная покупка списывает указанную цену и добавляет ровно один экземпляр; выбранное снаряжение не меняется.
  2. Покупка той же конфигурации новым намерением выдаёт другой ID при допустимом лимите.
  3. Двойное нажатие, параллельный повтор и потеря ответа после списания не дублируют покупку.
  4. Перезапуск Unity с сохранённым журналом восстанавливает результат в правильном аккаунте.
  5. Нехватка престижа, изменившаяся цена и исчерпанный лимит не приводят к частичной выдаче или списанию.
  6. Запоздалый ответ не уменьшает ревизию и не откатывает показанный баланс или инвентарь.
  7. Ошибка обновления инвентаря после Completed не превращается в повторную покупку.
  8. Купленное оружие доступно в следующем предматчевом выборе, но не меняет закреплённое снаряжение активного забега.
