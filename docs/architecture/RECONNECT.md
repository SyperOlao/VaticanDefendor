# Пауза и reconnect живого забега (этап 9)

`RunSimulationTime` принадлежит Server World забега. Его секунды, tick и `DeltaSeconds` продвигаются только при активной симуляции; на паузе `DeltaSeconds=0`. Транспорт, backend heartbeat, approval и доставка результата продолжают работать по реальному времени. `RunConnectionState` хранит состояние подключения отдельно от `RunLifecycle`: разрыв сам по себе не означает победу, поражение или новый забег.

Серверная политика задаётся окружением dedicated-процесса: `VD_SESSION_GRACE_SECONDS` (по умолчанию 10), `VD_SESSION_AFTER_GRACE=pause|continue` (по умолчанию `pause`), `VD_SESSION_RETENTION_SECONDS` (по умолчанию 300, больше grace) и `VD_SESSION_ON_EXPIRY=abandon|continue` (по умолчанию `abandon`). Это операционная политика процесса, не клиентский конфиг. Время grace и удержания измеряется временем Server World, которое идёт при паузе. Во время grace симуляция продолжает ход, если игрок не поставил ручную паузу. После grace выбранное действие применяется к игровым системам; сеть не останавливается. При `abandon` backend доверенно переводит назначение в `failed`, процесс завершается без постоянной награды. При недоступном backend сервер повторяет отказ с интервалом 5 с и остаётся закрыт для входа. При `continue` возврат запрещён, ручная и автоматическая пауза снимаются, симуляция идёт до игрового исхода. Уже завершённый бой обрабатывается правилами этапа 8, а не таймером удержания.

Клиент сохраняет `RunId` и удостоверение гостя в памяти процесса. Для возврата он получает новое ограниченное право от `POST /v1/runs/{RunId}/grant`; backend проверяет тот же аккаунт, текущее назначение, generation и живой heartbeat. Повторный запуск локального стенда использует тот же гостевой токен из игнорируемого Git `backend/.runtime/stage9-guest.json`. В рабочем приложении безопасное хранение гостевого удостоверения за пределами жизни клиента остаётся ограничением гостевой идентичности этапа 4. Секрет сервера в клиент не передаётся. Обновление права для кнопки Reconnect выполняется асинхронно; UI показывает подключение или явную ошибку.

Допустимо одно управляющее подключение. Новое подтверждённое подключение к тому же RunId забирает управление: сервер сразу меняет `RunSession.Connection`, обнуляет старый input и `GhostOwner.NetworkId`, запрашивает отключение прежнего соединения. После получения нового `NetworkId` сервер назначает существующего героя ему. Герой не привязан к `LinkedEntityGroup` соединения, поэтому разрыв не удаляет HP, позицию и боевое состояние. Команды боя, строительства и паузы принимаются только от текущего `RunSession.Connection`; запоздалые команды старого соединения отсекаются. Состояние экономики и занятых клеток принадлежит забегу. Повтор последней строительной операции с тем же ID и payload возвращает прежний результат; иной payload с тем же ID отклоняется `ConflictingOperation`; старые ID отклоняются `Duplicate`.

Netcode for Entities создаёт для нового соединения полный базовый набор ghost: герой, цели и враги, постройки и `RunEconomyView`. Сервер заново посылает предложения строительства, состояние церкви и RunLifecycle. `RunSnapshotRpc` передаёт RunId, время симуляции, паузу, количество построек и последний `ConstructionOperationId`. Клиент ждёт RPC, принадлежащего ему героя и заявленного количества построек перед показом игрового экрана; далее применяет обычные обновления ghost. Следующий локальный ID операции поднимается выше подтверждённого сервером. Срез времени и UI read model служат отображению; authoritative состояние остаётся на сервере.

## Воспроизведение

Собери Development client и dedicated server через `NetworkPrototypeBuild.BuildClient`/`BuildServer`. Подними локальные PostgreSQL и API через `backend/scripts/start-api-local.ps1` с выбранным release и **только тестовой** ставкой. Затем:

```powershell
backend/scripts/run-stage9-server.ps1 -ApiPort 8083 -GraceSeconds 3 -RetentionSeconds 50 -AfterGrace pause -OnExpiry abandon
backend/scripts/run-stage9-client.ps1 -ApiPort 8083 -Build 'structure.wall,2,0,4,0' -AttackEvery 0.5 -PauseAfterSeconds 2 -PauseValue 1
```

После строк `Player pause=1` и `replicatedStructures=3` останови только клиентский PID из `backend/.runtime/stage9-client.pid`, предварительно сверив путь процесса. Дождись в серверном логе `Player disconnected` и `Grace expired`. Повторный запуск скрипта клиента с `-Build 'structure.wall,2,0,4,0' -BuildOperationId 1 -PauseAfterSeconds 2 -PauseValue 0` использует того же гостя и RunId. Сверь `Reattached hero`, старый и новый tick паузы, три ghost, баланс, повтор операции и возобновление. Для проверки отказа после срока запусти отдельный сервер с `-RetentionSeconds 8 -OnExpiry continue`, дождись `Reconnect retention expired`, затем запусти клиент с тем же токеном: сервер и клиент должны сообщить `SessionExpired`. Для второго изолированного забега используй иной dedicated-процесс и порт.

Для проверки reconnect в том же клиентском процессе запусти клиент с `-ProbeReconnect` при работающем сервере. Проверочный MonoBehaviour использует тот же `NetcodeClientSessionPort`: ставит игру на паузу, разрывает транспорт, получает новое право через backend, подключается повторно и сверяет RunId, HP героя, золото и число построек. Успех записывается строкой `[Stage9Probe] Same client World reconnected` в клиентском логе и завершает процесс с кодом 0. Этот стенд проверен отдельными процессами в `Builds/Stage9/probe-{server-final,client-final2}.log`; визуальное нажатие кнопки Reconnect он не заменяет.

Падение dedicated-процесса и восстановление его ECS-мира не относятся к этому этапу: подтверждённый reconnect выполнялся только к живому Server World. Число награды за церковный уровень и Tycoon-улучшение остаются открытыми решениями этапа 8. Графический overlay и мобильный touch после reconnect ещё требуют отдельного визуального прогона.
