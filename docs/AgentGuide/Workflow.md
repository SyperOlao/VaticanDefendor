# Рабочий процесс и инструменты

## Обязательный рабочий порядок

- Рабочая среда — OpenAI Codex. Отвечать по-русски, если пользователь не просит иначе. Инструкции и инструменты Cursor не применять как правила Codex. Исторические Cursor-ссылки в документах сохраняют только исходный контекст.
- Сначала определить цель, границы изменения и затрагиваемые системы. Прочитать обязательные документы, проверить текущие исходники и состояние Git. Отделять действующие требования от предложений, исторических результатов и предположений.
- Делать минимальный правильный diff, повторять существующие соглашения проекта, сохранять чужие изменения и несохранённые данные. Не начинать постороннюю миграцию или очистку. Не создавать одноразовые слои абстракции без необходимости.
- Новые проекты и рабочие каталоги создавать вне C:, по умолчанию в M:/Prototypes; перед созданием проверить абсолютный путь. Существующие проекты и служебные настройки на C: можно изменять в рамках поручения.
- Отдельная команда «продолжить» означает: сначала выполнить новый вопрос или задачу текущего сообщения, затем продолжить последнюю незавершённую задачу с сохранением цели, разрешений, ограничений и результатов.
- Коммиты и push выполнять только по явному запросу пользователя. Перед коммитом проверить status, diff и log; затем add, commit и status. Не менять git config, не делать force-push, amend или skip hooks без отдельного разрешения. Заголовки коммитов — на английском, сообщение через HEREDOC; в PowerShell использовать here-string. Для GitHub использовать gh.
- Не запрашивать повторное разрешение на уже порученную работу. Неясности, влияющие на результат, уточнять своевременно и продолжать независимую часть работы. Не выдавать непроверенные предположения за установленные факты.
- Проверки выбирать по изменённой функциональности и реальному риску. Не запускать полные наборы и не повторять успешные прогоны без причины. Компиляция и проверки, необходимые для порученной задачи, разрешены; дополнительные проектные процедуры и ограничения читать в документах рабочего процесса.
- Пользоваться релевантными skills и доступными MCP/CLI. Об изменениях, принятых решениях, проверках и существенных ограничениях сообщать конкретно. Не выдавать наличие кода или старого отчёта за успешный текущий запуск.
- Строки отладки и логов внутри кода писать на английском. В интерфейсах использовать конкретные полезные тексты без рекламных слоганов и декоративных обещаний через «·».
- Не запускать субагентов и не делегировать работу без применимого явного разрешения. На моделях Astra действует установленный пользователем запрет по умолчанию; сложность задачи и свободные слоты его не отменяют.

## Размер инструкций и новые правила

- Целевой размер корневого AGENTS.md — 10–20 КиБ; жёсткий предел каждого AGENTS.md проекта — 32 КиБ (32 768 байт UTF-8). После изменения инструкций проверять фактический размер в байтах. Не дополнять короткий файл ради достижения нижней границы цели.
- В корне оставлять короткое обязательное ядро, карту тематических документов и порядок чтения. Подробности подсистем, архитектурные решения и историю хранить в соответствующих документах.
- Перед изменением подсистемы полностью прочитать её тематический документ, а при сквозной задаче — документы всех затронутых подсистем. Ссылки сами по себе не загружают содержание. Документы из карты являются обязательными инструкциями, а не справкой по желанию.
- Просьбы пользователя «закрепить», «запомнить», «добавить в AGENTS» трактовать как запись подробного правила в подходящий тематический документ. При необходимости создать документ и добавить его в карту. Отдельного подтверждения размещения не требуется. Сообщить пользователю, куда записано правило, с кликабельной ссылкой.
- При переносе сохранять смысл, ограничения, разрешения, даты и исключения. Не удалять подробности ради размера; проверять полноту переноса. Не оставлять действующее ограничение только в архиве.
- Сохранять область действия старых записей. Исторические задачи, разрешения на отдельный эксперимент, сроки и результаты проверок не являются новыми поручениями или доказательствами состояния текущей сборки. Учитывать явные позднейшие отмены и решения пользователя.
